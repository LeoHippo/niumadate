# 邀请页重设计说明（以本文为准，允许推翻之前的所有决定）

> 用户授权：「极大程度发挥想象力，从网上搜集相关流程/内容，可以推翻之前的想法，
> 完全按你的流程来写页面和动画，越好看越好，甚至可以把之前所有做的东西都推翻重做。」

## 一、调研：同类产品里反复出现的五条

看了数字请柬类产品（Paperlove 这类印尼数字请柬、Framer 上的 The Knot / Blossom Love、
Awwwards 上的信件/纸张类动效），共性很清楚：

1. **第一个动作永远是「打开」**：信封 → 火漆 → 拆开 → 取信。
   而且要**手能碰到**：手指拖拽、按住、撕开，而不是自动播放一段动画。
   我们现在是自动播放，朋友只是旁观者 —— **这一条最该推翻**。
2. **纸是主角，字是「印」在纸上的**：纸有厚度、有边、有压痕、有折痕阴影，
   文字跟着纸的形变走，而不是浮在纸上面。
3. 音乐几乎都有，而且第一屏就能看见开关。
4. 信息分层清楚：首屏只给「谁写给谁的」，时间地点放后面，最后才是回应。
5. 端到端为竖屏长页设计，一屏一件事、进度可见（这条我们已经有了）。

## 二、推翻清单

| 之前 | 为什么推翻 | 换成 |
| --- | --- | --- |
| 点「轻点继续」→ 自动播一段拆信 | 朋友是旁观者，参与感为零 | **手指按住火漆往下拖**：蜡被压裂、翻盖跟着手指翻开、纸被手指抽出来 |
| 小人替观众演所有过渡 | 它抢戏，而且「手没抓住纸」这种破绽很难藏 | 小人只在两处出现：拆信时跑来帮忙（彩蛋）、「不允许拒绝」那一支 |
| 每次翻页都是「小人把整张纸拖走」 | 三次之后就腻（用户原话：点了还想点） | 翻页换成**纸自己的动作**：折起来 / 翻过去 / 滑出去 / 抖一下，轮换 |
| 换页中间那 0.4 秒靠纱 + 扫光盖住 | 那仍然是「空」 | 改成纸边扫过 + 下一张纸从纸背后翻出来，没有空档 |

## 三、新的拆信分镜（第一阶段：做到能截图当海报）

0. 首屏：信封落在桌上（有影子、有落定回弹）。火漆在三角形正中，压着身份图案。
   角落一行小字：「按住蜡印，往下拉」。
1. **按住火漆向下拖**：蜡先被压扁（阻力感），再从正中裂开 ——
   四套身份四种裂法（沿用现有四套，但幅度更大、碎屑更多）。
2. 手指继续往下，**翻盖跟着手指的进度绕顶边翻**：手指拖多少、盖翻多少，不是定时动画。
3. 翻到位后纸自己往上顶出一截（表示信在往外走），随后**手指按住纸边往上抽**：
   纸一边出来一边变亮（离开信封的阴影）。
4. 纸铺满屏幕 → 这一屏就是那张纸 → 里面的字**像刚写上去一样**逐行出现。

关键差别：**前三拍由手指驱动**（pointermove 决定进度），手指不动它就不动。

## 四、视觉规则（重设计后统一遵守）

- 纸：不是纯白矩形 —— 纤维 + 极淡横向条纹 + 1px 深色纸边 + 四角微小翘起阴影；
  受压时产生**横向压痕**（渐变叠加），不是单纯缩放。
- 光：每个身份一束主光（暖红 / 玫粉 / 琥珀 / 灰蓝），换页时光从**纸的背后**扫过。
- 字：标题用身份字体，正文一律 15~16px、行高 1.9；每屏一句主句，第二句必须小一号。
- 节拍：任何动作遵循「预备 → 加速 → 过头 → 回弹 → 停稳」，
  4~5 秒的演出里至少 3 次速度变化，不允许匀速长滑。

## 五、分阶段（每阶段密集截帧自查 + 上线）

1. **交互式拆信**（本阶段）：按住蜡印拖 → 裂 → 翻盖 → 抽纸，全部手指驱动。
2. **纸的质感 2.0**：压痕、折痕、离开信封时的亮度变化。
3. **翻页动词表**：折 / 翻 / 滑 / 抖四种轮换，不再让小人干所有活。
4. **四套身份再拉一档**：光、字体、装饰、碎屑各不相同。
5. **最终回应**：答应的爆发 + 不允许拒绝那一支（保留小人）。

## 落地记录 · 第一步：拆信交到手上（已上线，已验收）

改版的第一个动作不是换配色，是把**开场的所有权**从代码手里拿回来：原来那段拆信
是「自动挡」—— 4.3 秒自己演完，观众是看客。现在是「手动挡」：手指按住火漆往下拉，
蜡被自己按裂、信被自己抽出来。用户要的「4 到 5 秒的感知」，靠的是他自己花掉的时间。

### 怎么做到的：一行关键帧都没改

那套 `@keyframes` 全部原样留着，只是被 `pause()` 之后把 `currentTime` 当进度条使：

| 状态 | 动画时间 | 画面 |
| --- | --- | --- |
| 手指在火漆上按下 | 0 | 信封闭着，蜡印完整 |
| 下拉 120px（全程 240px） | 2150ms | 蜡裂开、翻盖外翻、纸冒头 |
| 拉到 240px | 4300ms | 信封让开，纸长大到 290px 宽 |

好处是第一轮做的所有细节（四种火漆裂法、绕上边外翻、纸从信封口出来）全保留，
只是驱动源从"秒表"换成"手指"。拉一半松手 → 340ms 弹回没拆的样子；
只点一下（位移 < 6%）→ 2.7 秒自己走完；站着不动 3.6 秒 → 吸引模式自己开演，
但**任何时刻按住都能从当前进度夺过来接着拉**（不是从 0 重来）。

### 顺手改掉的一个产品级错误

原来的第一屏是一张"封面"（信封 + 「有一封邀请 / 拆开看看？」+ 按钮），
而且整个 `<section>` 上挂着 `onClick → goTo(index+1)`。
也就是说：**点大标题的人是直接翻页的，拆信这段压根没看见** ——
只有按对那个小按钮才看得到。用户那句「你的设计如果不让人们看到的话那就等于没设计」，
说的就是这个。现在这一页**就是那封信**：邀请函加载完，展开层立刻盖住整屏
（`.opening` 自带不透明的纸色底，不会出现"两个信封"），只剩信封 + 一行提示。
这也回到了最早定稿的分镜：「第一页就是背景 + 信封，背后什么都没有」。

### 三个只有"真的动手拉"才会暴露的 bug

1. **只按一次动画 → 信自己拆了，手指却从 0 开始拉。**
   暂停动画写成了 `useEffect([p])`：p 不变它就不跑。可 React 重渲染会**重建动画对象**，
   新对象是自己在播的（实测加载 1 秒后 19 个动画全跑到 583ms 且 running）。
   于是画面在演、`pRef` 还是 0，手指一拉整个错位。改成常驻的一帧一次：谁冒出来就按谁。

2. **拉到 100%，屏幕是空的。**
   `.op-env` 整层被 `op-env-slide-down` 淡出到 `opacity: 0`（注释还写着「纸留在原地」，
   但纸就是它的孩子）。定格量出来的事实：纸自己 `opacity=1 / scale=1.35` 一切正常，
   父层是 0 —— 这类 bug **只看纸的计算值永远查不出来**。
   现在信封整层只留一点"被拽动"的摇晃、收尾转回 0 度，下沉交给背板和折角自己做
   （`op-env-part-out`，纸不是它们的子节点）。

3. **我自己写的断言是错的。** 断言"动画 paused=false 才算在播"——
   而手动挡里动画**永远是 paused**（进度是 JS 每帧 seek 过去的）。
   断言写反了会把"对的东西"报成坏的；比不测更危险。

### 验收方式（以后拆信改动一律照这个来）

`node scripts/invite-gesture.mjs`（13 项，全绿）：用 CDP 派发**可信的鼠标事件**
真的按下去、分 12 步往下拖 240px，每步读一次动画进度，并落 7 张帧到 `.shots/gesture-*.png`
用眼睛看。它验的是"拉不拉得动"——之前那套暂停+seek 的截图工具验不了这件事：
暂停的动画永远在那儿，拉不拉得动它一个字都不说。

### 还欠着的（下一轮）

- 交接那一下还差 45px：纸收在中心 y=356，第二屏的卡片中心在 y=401。
  宽度已经对上了（纸 297px vs 卡片 300px），高度差在"卡片有内边距"这一层，
  再往上拉反而会让"抽出来"那一段变短。先记着，等第二屏的版式定下来再一起对。
- ⚠️ 别再用"暂停动画 + 手动设 currentTime"去截拆信的图了：现在进度由页面自己的
  常驻 rAF 每帧写回，外部 seek 会被它**下一帧覆盖掉**，截出来永远是闭着的信封
  （我被这个骗过一次，量到的数是对的、图是假的）。要图就走
  `scripts/invite-gesture.mjs`（真事件真拖拽，帧是实拍）。
- 火漆现在是一颗**有高光的球**，不像蜡。要的是"按下去会裂的一坨蜡"：
  哑光、边缘不规则、按下去有一圈压痕。
- 纸被"捏住"的那一下只有位移，没有**指头**：需要一个小手（或者纸边的凹陷+折痕高光）。

## 落地记录 · 第二步：四套身份换成"材料"（已上线，已四套各截帧）

原来四套只差一个色调 —— 同一张图换主色，摆在一起像四张色卡。现在按身份重定义的是
**材质与光**，规则全部写在 `opening.css` 末尾，选择器是
`body .opening[data-theme='x']`（写在元素自己身上，**不能靠祖先继承**：
展开层 portal 到 body，而 `invite-page.css` 顶部那条兜底声明写在元素上，会压过继承值）。

| 身份 | 信封纸 | 火漆 | 光 |
| --- | --- | --- | --- |
| brother | 牛皮色 `#e6d6b4`、偏灰 | 暗红、高光钝 | 暖黄顶光，暗角偏土 |
| sister | 奶油粉 `#f0e6d2`、最亮 | 玫瑰 + 珠光高光 | 原来那束暖光 |
| baby | 奶黄 `#f7edd0`、最柔 | 亮粉、高光最大 | 光最足、暗角最轻 |
| dadmam | 旧公文土黄 `#e3dcc6`、最沉 | 深褐、暗部最重 | 暗角最重、偏冷灰 |

暗角与顶光的颜色也提到了变量（`--op-vig` / `--op-top`），四套光才是四套。
火漆的"摊开痕"四套一起收细收淡（周期 14deg→9deg、浓度 0.055→0.045）：原来太像卡通太阳。
**没有**把浓度做成 var 塞进 `rgba()` 的 alpha 位 —— 浏览器不认的话整条 `background-image`
会被丢弃（连底色一起没，蜡直接消失），不值得为省几行冒险。

自己捅出来又自己修掉的一个可读性问题：提示条字色原来跟着 `--seal-hi` 走，
brother / dadmam 把它变成深棕，压在同样深的底上，「按住火漆，往下拉」几乎看不见。
现在只借 30% 身份色、其余用暖白，再补一道极淡暗影。

## 落地记录 · 第三步的实测诊断（翻页演出，尚未动手改）

取证工具：`node scripts/turn-shot.mjs`（造邀请 → 等拆信演完交接 → 可信鼠标点点「轻点继续」→ 每 250ms 实拍一帧，共 28 帧）。
第一组基线帧是 `.shots/turn-*.png`。看出来的三件事：

1. **小人没碰到纸。** push 这一路 0~1250ms 是「压」，但 500ms / 1500ms 两帧里小人都浮在卡片上方，
   中间空一大截，卡片只是自己在往下滑。这和当初「手没有真正抓到纸」是**同一个毛病**：
   小人的位移和页面的位移各写一套数。纸那一拍最后是靠"两者共用同一组 translate 数值"解决的
   （见上面的落地记录），翻页这一拍要照同一个办法治：先量出 `.puller-push` 与
   `.card-leaving-push` 在 0 / 1250ms 的实际 rect，再把小人的落点钉在卡片的受力点上。
2. **顶部回来的那一帧（3000ms）小人压在新页上沿**，像贴纸；按分镜这一路应该是
   **放下绳子把新页吊上来**，而绳子在画面里只剩一小截（`.move-rope` 的 `mv-rope` 要在这一路加长/加显）。
3. **节奏不统一**：翻页在 ~3.0s 就换了 DOM，而 `MOVE_MS = 4500` —— push 比 pull/fly 短一截。
   要么把 push 的时长对齐，要么承认三种动词本就该有不同节奏（但得看得出是**故意**的）。

改完照旧：`node scripts/turn-shot.mjs` 复拍同一组帧，和 `.shots/turn-*.png` 的基线逐帧对比，
两套冒烟 + `deploy.mjs --public --image`。

## 交接点 · 「结论」和「说两句」要合成一页（用户 2026-09-27 提）

用户原话：「之后那个结论和说两句放在同一页里面就好了不用再过渡了」。

**现状**：回答完之后是两处内容、两步到达 ——
1. 「结论」在 `Invite.tsx` 的 `Answer` 组件里，是状态一变（`invite.status !== 'pending'`）就渲染的
   `.invite-answered` 块（约 1400~1473 行）：欢呼小人 + 🎉 + 「好的，就这么定了 / 到时候见。」+ 一个
   「改成『那天不太行』」的按钮。
2. 「说两句」是独立一屏（`SCREENS` 最后一屏 `chat`，约 1210~1218 行），内容是一个可复用的
   `<Chat code={invite.code} messages={messages} onSent={onMessages} />`。

**要做的**（一次做完，别拆成半截）：
1. 在 `.invite-answered` 块里直接渲染 `<Chat … />` —— 结论 + 聊天框同页；
2. 因此 `Answer` 组件要多接两个 prop：`messages` / `onMessages`（渲染点约 1205 行，props 类型在
   `Answer` 的签名处），照 `ScreenBody` 里 `case 'chat'` 的用法传下去；
3. 去掉"回答完之后再翻到聊天屏"那一步过渡（用户说的「不用再过渡了」）—— 先确认它是由谁触发的
   （章节的 onClick 走 `goTo`，还是父级 `onRespond` 里推了一屏），再决定是拦住还是干脆不再用那一屏。

**注意**：`chat` 这一屏在"重新打开一条已经回过的邀请"时仍然要用（那时没有结论块），
所以别直接删掉它，只断开"回答之后自动过去"这条路径。
